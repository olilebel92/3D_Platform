Spell System Overhaul
In Progress
April 9, 2026
Spell Cast State Machine
  • SpellCaster rewritten with 4-state machine: Idle → PreCast → Pending → Channeling
  • SpellData expanded: spellType (Cast / Buff / Aura / Channel), castStartDelay, castTime, throwAnimLeadTime per spell
  • Multi-projectile support: projectileCount + spreadAngle fields on SpellData
  • Server resolves spell prefab by name from NetworkManager registry — no ordered array or enum mapping needed
Interrupt System
  • Per-spell interrupt rules: movementInterruptGrace + damageInterruptGrace configurable on SpellData
  • Stun always bypasses both grace windows and cancels the cast immediately
Status Effects
  • StatusEffectHandler — stun duration tracking, highest-value-wins (no stacking), calls SpellCaster.CancelByStun() on apply
  • PlayerController honours IsStunned — all movement and input blocked while stunned
Player Name Tags
  • PlayerNameTag — world-space TMP billboard above each player, syncs to LobbyPlayer.PlayerName NetworkVariable
  • Billboards to Camera.main each LateUpdate; hidden for the local owner when configured
  • Solo fallback: shows "Player" when NGO is not active
Cast Bar UI
  • SpellCastBarUI fully event-driven — subscribes to OnCastBegin / OnCastComplete / OnChannelBegin / OnChannelEnd
  • Orange fill for casting, blue for channeling; channel tick resets bar on each tick
WIP: Spell system framework is in — wiring remaining spell types (Buff, Aura) and integrating status effects into enemy hits. Ships when all four spell types have at least one working implementation.

Confirmed — Gameplay Loop

Session-based · Persistent Character Locked In — April 2026

The gameplay loop is confirmed. Every feature decision should serve this loop. If a feature doesn't make the dungeon run or the hub better, it goes on the post-V1.0 list.

Hub / Town — persistent social space, upgrade stations, dungeon entrance
   Party forms in Lobby (2–4 players) — enter dungeon together
Dungeon Floors — rooms of enemies, traps, mini-bosses, locked doors
   Clear the room — door opens — next floor
Boss Room — boss fight at end of the dungeon
   Defeat boss — loot drops — return to Hub
Upgrade — spend XP on skill tree · craft/equip loot · prepare next run
Harder Dungeon Tier — higher floor cap, stronger enemies, better rewards
Co-op firstDesigned for 2–4 players. Solo is supported, not the focus.
Persistent characterXP, gear, skill points carry over permanently between sessions.
Open skill treeClass sets starting position and base stats. No locked nodes — build anything.
Dungeon tiersEscalating difficulty — not open world. Each session has a clear start and end.
Priority Recommendations
  • 1
    Prove the loop before polishing anythingV0.6 should be a rough dungeon run that works end-to-end. Ugly is fine. The goal is: enter, fight rooms, boss, return to hub, XP gained. Everything else is polish on top of that.
  • 2
    Dungeon room system replaces WaveManager at V0.9The current WaveManager sends waves at the player. The target design uses rooms — you enter, clear enemies, the door opens. This is a deliberate architectural shift that needs a dedicated milestone.
  • 3
    Hub before contentA minimal hub — a flat area with a dungeon entrance — should exist from V0.7. Players need somewhere to return to for the loop to feel right, even as a placeholder.
  • 4
    Terrain design only after dungeon is builtDon't invest in world design until V1.4. You don't know what the hub needs to contain or how the dungeon entrance fits until the dungeon system is working.
  • 5
    Save system after V1.0 — data must be stable firstBuilding the save system before class differentiation, the skill tree, and gear are locked means rewriting it. Wait until V1.1 when the data structure won't change anymore.
  • 6
    Skill tree: one shared open tree, class = starting positionNo locked nodes. Class sets base stats and start point on the tree. Adding new classes later is just defining new start positions — no new trees to build.
  • 7
    Ask one question for every feature: does it serve the loop?Does this make the dungeon run better, or the hub more engaging? If the answer is no, it goes on the post-V1.0 list. This is the fastest path to a shippable game.

Risks to Watch
High — WaveManager to Room System

The current wave system is the opposite of the room-based target design. This architectural shift at V0.9 is the largest single refactor before release. Plan a full dedicated session — don't combine it with other work.

High — Building content before the loop

Adding spells, enemies, and gear before V0.9 feels like progress but isn't. The loop has to work end-to-end first. Content fills a working game — it doesn't make an incomplete one fun.

Medium — Hub scope creep

The hub can become a full game unto itself — NPCs, shops, quests, housing. Keep V0.7 as a flat area with a dungeon entrance. The rest comes at V1.4 when the dungeon system is stable.

Medium — Networked combat complexity

Server-authoritative damage and hit detection are easy to get wrong. V0.4 and V0.5 need dedicated testing sessions. Latency issues are much harder to fix after the systems are built on top.
