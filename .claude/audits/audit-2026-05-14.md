## 📡 Networking Safety (NGO-specific)

1. **`TargetSelector.cs:108–111` — `OnDestroy` override does NOT call `base.OnDestroy()`.**
   NGO's `NetworkBehaviour.OnDestroy` unregisters the instance ID and runs internal cleanup. Skipping `base.OnDestroy()` leaks NGO state on every disconnect / scene unload. Compare with the rest of the codebase — `Playerattack.cs:132–135`, `PlayerController.cs:265–268`, `PlayerNameTag.cs:100–104`, `SpellCaster.cs:291–296` all correctly chain to `base.OnDestroy()`. **Fix: add `base.OnDestroy();` as the first line.**

2. **`Enemyreward.cs:66–114` — `OnDestroy` override missing `base.OnDestroy()`.** Same class of bug as #1. Compounded by the fact that this override runs heavy reward logic (XP grant, drops, RPCs) — if `base.OnDestroy()` is needed for the spawn manager to deregister the despawned object before the next frame, this could mis-fire on rapid spawn/despawn cycles. **Fix: add `base.OnDestroy();` after the early returns.**

3. **`LobbyChatManager.cs:60–63` — `OnDestroy` override missing `base.OnDestroy()`.** Pre-existing (not modified in window) but worth flagging — third NetworkBehaviour with the same bug pattern.

4. **`EnemyAI.cs:89–103` — `ApplyData()` runs in `OnNetworkSpawn` *before* the `IsServer` gate, on all clients.**
   `ApplyData()` writes to `HealthSystem.maxHealth` AND `currentHealth` (line 448–449). Non-server clients will set their local HealthSystem state, then the server's first `NetworkHealth.Value =` write is broadcast via the NetworkVariable. The window is narrow (≤1 frame) but state diverges across clients between Spawn and the first NV broadcast. Lower risk: maxHealth value is identical (same SO), so the divergence is invisible — but the pattern violates "Damage must flow server → client" from `.claude/rules/networking.md`. **Fix: guard the `HealthSystem` writes inside `ApplyData()` with `if (IsServer)`, or only call `ApplyData()` inside `if (IsServer)` in OnNetworkSpawn and trust the NetworkVariable for clients.**

5. **`WaveManager.cs:282–302` `ApplyDifficultyScaling` → `EnemyAI.OnNetworkSpawn.ApplyData` race — difficulty scaling gets wiped if `_data` is assigned on the prefab.**
   Sequence:
   1. `WaveManager.SpawnWave` (line 255) Instantiates the enemy prefab.
   2. `ApplyDifficultyScaling(enemy)` (line 257) multiplies `health.maxHealth` and `ai.attackDamage`.
   3. `netObj.Spawn(...)` (line 268) — triggers `EnemyAI.OnNetworkSpawn` → `ApplyData()` → overwrites the just-scaled `h.maxHealth` and `attackDamage` back to the SO baseline.
   Result: every WaveManager-spawned enemy with `_data` assigned to its prefab ignores wave scaling. Real bug. **Fix: in `EnemyAI.OnNetworkSpawn`, only call `ApplyData()` when `_data != null` AND `h.maxHealth == 0` (the un-touched default), or have WaveManager apply scaling AFTER `Spawn()` by calling a new public `ApplyDifficultyMultipliers(hpMult, dmgMult, spdMult)` on the AI.**

6. **`SpellCaster.ComputeRawDamage` (line 975) runs on the client and the result is sent in `SpawnProjectileServerRpc` (line 734) / `SpawnTargetLockedServerRpc` (line 914).**
   The server trusts whatever damage the client computed. A malicious client can send arbitrarily high `rawDamage`. Known trade-off (allows per-client skill-tree/equipment lookups without replicating all inventory state) but worth recording as a known design ceiling for any future "competitive" mode. No action — flagging for awareness.

7. **`GodMode.cs:30–34` — `Update()` reads keyboard input with no `IsOwner` / `IsLocalPlayer` check.**
   The script is a `MonoBehaviour` so there's no NGO ownership concept. If attached to the Player prefab in MP, every spawned Player on this machine (host + remote players' representations) would respond to `Digit0` simultaneously. In practice only one Player is local, so the bug only manifests if remote-player Players carry the GodMode component. Low risk — but if you ever do dedicated server or spectator mode this becomes user-visible. **Fix: gate with `GetComponent<NetworkObject>()?.IsOwner` or attach only to the local-spawn prefab variant.**

## 🔗 Coupling Issues

1. **`EnemyData` / `EnemyAI._data` / `WaveManager.ApplyDifficultyScaling` overlap.**
   Three independent code paths now mutate `HealthSystem.maxHealth` and `EnemyAI.attackDamage`: the prefab's Inspector values, `EnemyData` SO override, and `WaveManager` scaling. The ordering bug in section #5 above is the symptom; the root cause is that scaling lives in WaveManager and data lives in EnemyData and they don't compose explicitly. **Risk: any future system that wants to bump enemy stats (e.g. difficulty modifiers, elite affixes) has to either pre-empt `ApplyData()` or post-process. Action: pick one canonical entry point — `EnemyAI.ApplyDataWithScaling(data, multipliers)` — and route both spawners through it.**

2. **`SpellCaster.ComputeRawDamage` reaches into four singletons** (`SkillTreeManager.Instance`, `ExperienceManager.Instance`, `PlayerInventory.Instance`, plus implicit `_active.school` enum coupling) in one method. New schools (Lightning) already added complexity. Each new school requires editing this method + adding paired flat/pct properties on SkillTreeManager. **Risk: adding a 5th school (e.g. Ice) means six lines of SkillTreeManager properties, six lines in `RefundAll`, and one new pair in `ComputeRawDamage`. Action: replace per-school properties with `Dictionary<SpellSchool, (float flat, float pct)>` keyed by enum, populated in `LearnNode`/`RefundAll`.**

3. **`EnemyAI.RefreshNearestTarget` (line 193) uses `FindGameObjectsWithTag("Player")` while the rest of the v0.2 codebase migrated to `PlayerController.All`.** Inconsistency makes it look like the static registry exists for some scripts but not others, inviting future regressions where someone "fixes" `RefreshNearestTarget` to use `.All` and breaks a server-only path. Same issue in `Enemyreward.cs:89, 121, 134` and `EnemyAI.DealDamageClientRpc` at line 357. **Action: route everything through `PlayerController.All` and delete the tag-based lookups.**

4. **`EnemyAI.Start()` (line 145–147) directly looks up `EnemyHealthBarManager.Instance`** and calls `AttachTo`. Manager → managed coupling is fine, but managed → manager is the reverse direction — every new visual subsystem (nameplate, status icons, etc.) will end up appended to EnemyAI's Start. Better as an `OnEnemySpawned` event on EnemyAI that managers subscribe to.

5. **`TargetSelector.OnDestroy`, `EnemyAI.OnNetworkSpawn`, `EnemySpawner.SpawnEnemy`, and `WaveManager.SpawnWave` are now all coupled to the shape of the enemy prefab** (NetworkObject, EnemyAI, HealthSystem, EnemyReward, EnemyTracker, NavMeshAgent, Animator, Renderer hierarchy). Any change to the prefab structure ripples through all four. Not new, but the surface is now larger.

## ⚠️ Design Smells & Runtime Risks

1. **`EnemyAI.cs:228–248 ApplySeparation()` — `Physics.OverlapSphere` allocates `Collider[]` every frame, per enemy.**
   Runs in `Update()` on every server-side enemy (after `ShouldRunAI()`). A wave with 20 enemies = 20 array allocs per frame = ~1200 allocs/sec at 60Hz. The exact pattern that `IsoCursorAim` and `ChainLightning` were just refactored away from. **Fix: switch to `Physics.OverlapSphereNonAlloc` with a static `Collider[16]` buffer.**

2. **`EnemyAI.cs:193, 357` and `Enemyreward.cs:89, 121, 134` — `GameObject.FindGameObjectsWithTag("Player")` in hot/spammed paths.** RefreshNearestTarget is throttled to `retargetInterval` (default 1s) so it's OK in isolation, but `Enemyreward.OnDestroy` runs once per enemy kill which can be many per second on later waves, and `DealDamageClientRpc` runs per attack tick. All have a faster alternative in `PlayerController.All`. **Fix: replace with `PlayerController.All` iteration.**

3. **`TargetSelector.s_smoothMeshCache` (line 79) is a static dictionary keyed by mesh instance ID, with no eviction.** Each unique enemy mesh adds one `Mesh.Instantiate()` worth of memory (verts × float3 + uv2). Over a long session with many enemy variants the cache only grows. Low priority — but worth a `s_smoothMeshCache.Clear()` on scene unload.

4. **`TargetSelector.EnsureSmoothNormals` (line 269) writes UV2 on the cloned mesh.** If the toon shader stores anything in UV2 (occlusion, second texture coords, vertex baked colour), the outlined enemy will lose it. The Toon Shaders Pro pack might genuinely use UV2 — worth confirming with their docs before the next render-pipeline tweak.

5. **`TelegraphProjector.RebuildDecal` (line 288) and `ShowRange` (line 154) destroy and recreate a 256×256 Texture2D + Material on every call.** That's a 256KB allocation + GPU upload per spell cast. Same shape gets rebuilt identically — a per-shape cache (key by `TelegraphShape × tint`) would eliminate it. Low-priority but visible in profiler during spell-spam.

6. **`SpellCaster.cs:944 FindRegisteredPrefab` / `FindRegisteredGameObject` walk `NetworkConfig.Prefabs.Prefabs` linearly on every spawn.** Fine for small prefab lists, will get sluggish past ~200 entries.

7. **CLAUDE.md hard-rule violation: `DontDestroyOnLoad` in `CursorManager.cs:48` and `MusicManager.cs:57`.** The project rule reads "Never use `DontDestroyOnLoad()` unless explicitly asked". Both are intentional per recent commits ("CursorManager: DontDestroyOnLoad + init in Awake" / MusicManager design). Either the rule should be updated to permit persistent UI singletons, or these should move to a single bootstrap object with a scene-load reset. Right now the codebase contradicts its own CLAUDE.md — surfaces as confusion next time anyone audits.

8. **`SpellCaster.CancelCast()` (line 213) — removes the cooldown for any cancelled cast.** Documented but exploitable: spam-cast + spam-cancel denies any cast-time penalty. Possibly fine for SP, but in MP a cooldown-locked combat-encounter spell can be free-spammed. Design note.

9. **`SpellCaster.cs:944 / 952 FindRegisteredPrefab` falls back to `Resources.Load<GameObject>(prefabName)` if not in NetworkConfig.** That's a synchronous filesystem hit on every spell cast that doesn't match a registered prefab — silent perf cost on misconfigured prefabs. **Action: cache results or log+throw.**

10. **`EnemyAI.cs:107-148 Start()` runs renderer fix-up + manager attach on `Renderer`s found via `GetComponentsInChildren<Renderer>()` — which includes the freshly-instantiated `EnemyHealthBar` if it was added BEFORE this scan.** Currently safe because `Start()` runs before `EnemyHealthBarManager.Instance.AttachTo` (line 147), but it's an ordering trap: any future code that attaches visual children in `Awake()` will have their materials tampered with.

11. **`EnemyHealthBarManager.cs:43` indentation is broken** (`if (renderers.Length == 0)` has no leading whitespace, breaking the visual structure of `ComputeTopY`). Compiles fine but reads as a near-bug. **Fix: re-indent.**

12. **No `Animator.StringToHash` cache verified** — all caching is in place (e.g. `EnemyAI.AnimWalk`, `EnemyAI.AnimAttack`, `EnemyAI.AnimIdle` at lines 66–68). Good.

13. **`TargetSelector.cs:240–249 SetOutline` allocates a fresh `Material[]` array on every hover frame.** Hover-frame is not per-frame (only on new hover transition via `UpdateHover`), so the cost is bounded. Still — pre-allocate a single `Material[N+1]` reused per renderer if outline thrash becomes visible.

14. **No legacy `UnityEngine.UI.Text` introduced in this window** (grep confirms `TMP_Text` / `TextMeshProUGUI` everywhere new). Hard rule preserved.

15. **No legacy `Input.GetKey` / `Input.GetAxis` introduced** (grep confirms `Keyboard.current`, `Mouse.current`, `Gamepad.current` everywhere new). Hard rule preserved.

## 🚨 Priority Fix List

1. **`base.OnDestroy()` missing in 3 NetworkBehaviour overrides — NGO state leak.**
   - **Risk**: Internal NGO instance-ID and despawn bookkeeping is skipped on every disconnect / scene unload. Manifests as ghost objects in `NetworkManager.SpawnManager.SpawnedObjects`, late `OnValueChanged` callbacks firing on destroyed components, and slow memory growth over long-lived sessions. Hits host AND clients.
   - **Fix**: Add `base.OnDestroy();` as the first line in `TargetSelector.cs:108`, `Enemyreward.cs:66`, and `LobbyChatManager.cs:60`.

2. **WaveManager difficulty scaling is wiped by `EnemyAI.ApplyData` whenever the prefab has `_data` assigned — wave 30 is no harder than wave 1.**
   - **Risk**: Late-wave content stops scaling. Players notice as a "difficulty cliff" where wave 20+ feels identical to wave 5. Host-side bug; clients see whatever the server spawns, so it's silent in MP — the bug is in the spawning sequence on the server.
   - **Fix**: In `EnemyAI.cs:89-103 OnNetworkSpawn`, change `ApplyData();` to run only when `_data != null && healthSystem.maxHealth <= _data.maxHealth`, OR move WaveManager's `ApplyDifficultyScaling` to AFTER `netObj.Spawn()` by adding a public `EnemyAI.ApplyDifficultyMultipliers(float hpMult, float dmgMult, float spdMult)` method and calling it from `WaveManager.cs:268+`.

3. **`EnemyAI.ApplyData()` writes `HealthSystem.currentHealth` on all clients in MP — violates server-authority rule.**
   - **Risk**: Client-side `currentHealth` diverges from the server's `NetworkHealth` until the first NV broadcast. Subtle visual flash on spawn; can become a real bug if any future client-side system reads `HealthSystem.currentHealth` instead of `NetworkHealth.Value`.
   - **Fix**: In `EnemyAI.cs:430 ApplyData`, gate the `HealthSystem` writes behind `if (NetworkManager.Singleton == null || !NetworkManager.Singleton.IsListening || IsServer)`.

4. **`EnemyAI.ApplySeparation` allocates `Collider[]` per frame per enemy — ~1200 GC allocs/sec on a 20-enemy wave.**
   - **Risk**: GC stutter at high wave counts; hot in profiler. Hits server (in MP) and solo player.
   - **Fix**: Replace `Physics.OverlapSphere` at `EnemyAI.cs:232` with `Physics.OverlapSphereNonAlloc(transform.position, _separationRadius, s_separationBuffer)` and a `private static readonly Collider[] s_separationBuffer = new Collider[16];` field. Mirror the `ChainLightning.s_overlapBuffer` pattern.

5. **`FindGameObjectsWithTag("Player")` in `EnemyAI.RefreshNearestTarget` / `DealDamageClientRpc` and `Enemyreward.OnDestroy` / nearest-player / client-id lookup — inconsistent with the v0.2 `PlayerController.All` migration and slower.**
   - **Risk**: Inconsistent style invites regressions; per-kill tag scans are wasteful on later waves; one of these (DealDamageClientRpc) runs per attack tick.
   - **Fix**: Replace each call with `PlayerController.All` iteration. Five touch points: `EnemyAI.cs:193, 357`; `Enemyreward.cs:89, 121, 134`.
